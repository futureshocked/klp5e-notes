KiCad Like a Pro, 5th Edition — Volume 2

Creating Custom Symbols

In Volume 1 you learned to find the symbols and footprints you needed. You searched KiCad’s built-in libraries, you pulled parts from reputable online repositories, and you managed them in your library tables. That is the standard sourcing tree where you will be able to find almost every part you will ever place. In my work, I rarely ever have trouble finding a part I need, unlike in the early few years of KiCad, where the built-in library was small and online repositories only supported established CAD applications. Despite this, sooner or later you will want a component that you can’t find anywhere, in which case you will have to design the part yourself. That’s the skill this chapter teaches, and it is the first thing that makes Volume 2 a book about producing rather than consuming.

You will learn this new skill in a hands-on way. We will author the symbol we’ll need in the capstone project, the ‘DRV8833’ dual H-bridge motor driver, so that by the time you reach that capstone, the part will be available in your own library. The DRV8833 is an excellent first symbol to draw because of its diversity. It has sixteen pins (plus one, as you’ll see), which gives this work a realistic complexity. Those pins fall into several functional groups, which makes arranging them on the symbol an excellent sub-exercise in its own right (Figure 1.1). I will work from the manufacturer’s datasheet throughout (https://www.ti.com/lit/ds/symlink/drv8833.pdf), because the datasheet is the single source of truth for what the pins are, what they are called, and what they do. Before you author any part, always download its datasheet and keep it open beside you.

Figure 1.1: Where this chapter is going: the finished DRV8833_PD symbol. The four logic inputs and “nSLEEP” run down the left edge, the two bridges’ outputs and sense pins are grouped on the right with the “nFAULT” flag below them, “VM”, “VINT” and “VCP” sit along the top, and “GND” and the thermal “PAD” leave from the bottom. The text outside each connection point is the pin’s electrical type, and the number above each pin line is its package pin number.

Symbol Editor

A schematic symbol is a small drawing that exposes functionality so that it works with other symbols within the KiCad schematic editor. A symbol has a body, usually a plain rectangle, that represents the part on the sheet. It also has pins, each with a number, that matches the physical package, and a name that tells you what the pin does. Likewise, it carries a reference designator, the “U” or “R” that annotation will later number automatically in the schematic, and a value, which is the part’s name. Everything else in the symbol, such as its footprint, its datasheet, and its supplier code, is stored as a property called a field, which we come to next. If you draw those few things correctly, you’ll have a symbol that works correctly throughout the rest of the workflow.

Start the Symbol Editor. You can open it from the main KiCad project window, which is the route I take here, or from the button in the schematic editor’s top toolbar; either way you arrive at the same place, an editor that looks like a simplified schematic canvas with a library tree down the left side (Figure 1.2).

Figure 1.2: Opening the Symbol Editor from the main KiCad window. (1) The “Symbol Editor” entry in the project window’s launcher. (2) The editor it opens, with the library tree on the left, an empty canvas in the middle, and a title bar reading “[no symbol loaded]” because you have not made anything yet.

Because every symbol must be stored in a library, the first step is to make one of your own. Choose “File” and then “New Library”. KiCad asks you to name the file and choose where on disk it goes, and then, at the bottom of the same dialogue, whether to add the library to the “Global” table, so it is available to every project, or the “Project” table, so it belongs to this project alone (Figure 1.3). Those are two independent choices: the folder decides where the file sits, and the table decides who can see it. For a part you expect to reuse, like this motor driver, choose the global table. I keep my own parts in a library called peters_custom_Library, and I will use that name for the rest of the chapter. KiCad writes the file with a .kicad_sym extension, registers it for you so that you never have to touch the library table by hand, and selects it in the tree so that you can start work immediately (Figure 1.4).

Figure 1.3: The “New Symbol Library” dialogue. The file is named peters_custom_Library.kicad_sym at the top, and the two radio buttons at the bottom decide which table it is registered in; the arrow points at “Add new library to global library table”, the choice this chapter makes. The file itself is being saved into the chapter’s project folder, which is convenient while you are following along, though a library you mean to reuse is better kept somewhere stable outside any single project.

Figure 1.4: The new library appears in the Symbol Editor’s library tree, already selected, in alphabetical order among KiCad’s own libraries.

Your library is already selected, so click “New Symbol” in the top toolbar. KiCad asks for a name and a reference designator (Figure 1.5). I name this one DRV8833_PD, where the _PD suffix is my own habit for marking symbols I authored, so I can quickly tell my parts from the stock ones, and I set the designator to “U”, because it is an integrated circuit. Leave “Number of units per package” at 1; we come to what that setting is for later in the chapter. Click “OK”, and drag the designator and value text clear of the centre so that you have room to work.

Figure 1.5: Creating the symbol. (1) The “New Symbol” button, with peters_custom_Library selected in the tree beside it. (2) The symbol name, DRV8833_PD. (3) The default reference designator, “U”. (4) “OK” creates the empty symbol and opens it on the canvas.

Now draw the body. Pick the rectangle tool from the right toolbar and drag a box around the centre of the sheet (Figure 1.6). Don’t fuss over the exact size yet; you can resize it via the handles that appear when the rectangle is selected and active, once the pins are on.

Figure 1.6: Drawing the body. (1) The rectangle tool in the right-hand toolbar. (2) The rectangle dragged out across the origin. The asterisk beside DRV8833_PD in the library tree is KiCad reminding you the symbol has unsaved changes.

The convention that makes an IC symbol readable is to group its pins by what they do (their role), not by the order they appear on the package. In Figure 1.1 you can see the arrangement this symbol ends up with. The four logic inputs, “AIN1” (16), “AIN2” (15), “BIN1” (9) and “BIN2” (10), together with the “nSLEEP” enable (1), run down the left edge, because inputs belong on the left by convention. The right edge carries the two bridges in turn: “AOUT1” (2), “AOUT2” (4) and the “AISEN” sense pin (3), then “BOUT1” (7), “BOUT2” (5) and “BISEN” (6), with the open-drain “nFAULT” flag (8) below them. The motor supply “VM” (12) and the two internal-rail pins, “VINT” (14) and “VCP” (11), sit along the top, and the two pins that return current to ground, “GND” (13) and the thermal “PAD” (17), leave from the bottom. Placing pins by function is the one big difference between authoring a symbol and authoring a footprint. While a footprint must copy the package exactly, a symbol is free to arrange its pins so that the schematic is easy to follow.

One pin on this symbol is not in the datasheet’s numbered list. The HTSSOP package carries an exposed thermal pad on its underside, and that pad is an electrical connection to ground as much as it is a heat path. The correct way to design this symbol is to include this thermal pad in the symbol as an exposed pin, like any other pin. I number it 17, name it “PAD”, and place it at the bottom of the body beside “GND”. The datasheet’s pin table stops at sixteen, so that number is a convention I am choosing rather than a fact I am copying, and the only rule that matters is that the footprint you draw in the next chapter uses the same one. Leaving the pad off the symbol altogether is a common shortcut, but it means that the board ends up with a chip soldered to a pad of copper that is not connected to anything else on the board.

Start with the five pins that run down the left edge, the four logic inputs and “nSLEEP”, and place them by hand. Five is enough to learn the dialogue properly. I’ll show you how to add the other twelve arrive by a faster route in a moment. To add a pin, click the pin tool in the right toolbar and fill in the “Pin Properties” dialogue: the name, the number, an electrical type, and a graphic style. The first three all come straight out of the datasheet, and Figure 1.7 shows where each one is read from.

The name is the pin’s name as the package drawing and the “Pin Functions” table give it, “AIN1” rather than “logic input 1”. The number comes from that same table, and this is where mistakes commonly happen. The “Pin Functions” table lists a separate column of numbers for each package the part is sold in, and the numbers do not agree: the DRV8833 has a “WQFN” column and an “HTSSOP, TSSOP” column, so “AIN1” is pin 14 in one and pin 16 in the other. We are drawing the HTSSOP part, so 16 is the number that belongs on this symbol. Read the wrong column and every pin you place will be plausibly, invisibly wrong, and you will not find out until a board comes back with a chip wired backwards. The pin’s role comes from the “I/O” column and the description beside it, and that is what you turn into an electrical type.

Figure 1.7: The “Pin Properties” dialogue for AIN2, with the datasheet open beside it. The ringed button at the top right is the pin tool. One arrow ties the boxed “Pin name” and “Pin number” fields to the package pinout drawing, where pin 15 is AIN2. The other ties the AIN1 pin already on the canvas back to its row in the “Pin Functions” table, where the HTSSOP column reads 16 and the description reads “Bridge A input 1”. Notice that the same row gives 14 in the WQFN column.

The electrical type is the field that matters most. It is what the Electrical Rules Check (ERC) reads to decide whether a pin is being driven correctly. Most of the seventeen pins are straightforward, but four of them, “AISEN”, “BISEN”, “VCP” and “VINT”, are easy to get wrong, so read those rows of the datasheet carefully:

  • “VM” and “GND” are ‘power input’1, the motor supply and the ground return.
  • The four logic inputs, “AIN1”, “AIN2”, “BIN1” and “BIN2”, together with the “nSLEEP” enable, are ‘input’.
  • The bridge outputs, “AOUT1”, “AOUT2”, “BOUT1” and “BOUT2”, are ‘output’.
  • The open-drain “nFAULT” is ‘open collector’, so that the ERC understands it needs a pull-up.
  • “AISEN” and “BISEN” are ‘passive’. They are the two bridges’ ground returns, which you either tie straight to ground or run through a sense resistor.
  • “VCP” is ‘passive’ too. It is the charge pump’s own node, bypassed to “VM” and driven by nothing outside the chip.
  • “VINT” is ‘power output’, because it is the output of an internal regulator rather than a supply you feed.
  • The thermal “PAD” is ‘power input’, like the “GND” pin it joins.

The graphic style, by contrast, is purely cosmetic. It is worth spending the necessary time here to get the electrical types right so that the ERC can catch and return real problems later.

A pin lands wherever you click it, so once all five exist, drag them onto the left edge of the rectangle (you may need to rotate them to fit in place). The four logic inputs should be grouped together at the top, and “nSLEEP” should sit a little apart below them, since it enables the chip rather than driving a bridge (Figure 1.8). Nothing in KiCad enforces this. Inputs on the left is a convention, not a rule, and it is worth following because someone who opens your schematic will likely look for the inputs on the left without being told to.

Figure 1.8: The five hand-placed pins, moved onto the left edge. Each one shows its name inside the body, its number above the pin line, and its electrical type, “Input”, outside the connection point. The other three edges are still bare.

Pin Table

Placing seventeen pins one dialogue at a time is straightforward but slow, and KiCad 10 gives you a much faster way to do it. Now that you have done five by hand, you know exactly what that faster way is doing for you in the background. Open the ‘Pin Table’ from the top toolbar. This will show a spreadsheet view of every pin and its properties. Beneath the grid, at the lower right of the dialogue, sit two panels: “Export”, which writes the pins out to a file, and “Import”, which reads a set of pins in. The “Import” panel holds a “From File…” button and a “From Clipboard” button, and it is “From File…” that loads a whole set of pins from a CSV file in one step. You can prepare the CSV in any spreadsheet program. Provide one row per pin with a header row naming the columns (name, number, electrical type, and so on), and KiCad will map the columns by their headers. For a part with this many pins the import offers an accelerated way to define them, and it makes the datasheet’s pin table the literal source of your symbol. I use the table for every part I author now, and it has a full recipe of its own in Chapter 10, including how to export an empty template and fill it in. What follows here is just enough of that recipe to finish this symbol.

The twelve pins you have not placed yet are waiting for you as drv8833-pins-remaining.csv, in the ch08-drv8833 project folder that ships with this book, alongside the capstone this part is being drawn for. Before you import it, look at the two radio buttons in the “Import” panel, because the choice matters here and the wrong one is easy to click past (Figure 1.9). “Replace all existing pins” throws away what is in the table and installs the imported set in its place, which would delete the five you just drew. “Append to existing pins” adds the imported rows and leaves everything else alone, which is what you want. Select “Append to existing pins”, click “From File…”, and choose drv8833-pins-remaining.csv in the file dialogue that opens. If you would rather start the whole part from the table instead, drv8833-pins-all.csv sits in the same folder, holds all seventeen pins, and is meant to be imported with Replace.

Figure 1.9: Importing the remaining twelve pins. (1) The Pin Table button in the top toolbar. (2) The five pins you placed by hand, already listed with their positions. (3) The contents of drv8833-pins-remaining.csv, one row per pin under a header row that names the columns (the CSV content is open in a text editor that I have placed over the Pin Table window). (4) The import controls, with “Append to existing pins” selected rather than “Replace all existing pins”, and “From File…” waiting to be clicked.

The table should settle at seventeen rows, and the summary line above the grid offers a quick way to confirm this: “Pin numbers: 1-17”, “Pin count: 17”, “Duplicate pins: none” (Figure 1.10). Every number from 1 to 17, present exactly once, nothing repeated. If that line says anything else, you have imported the wrong file, or imported it twice.

Figure 1.10: The Pin Table after the import, with all seventeen pins present and the summary line confirming it. Look at the two position columns on the right: the five pins you placed by hand carry their coordinates, and the twelve imported ones all read 0 mils, because a CSV describes what a pin is, not where it goes.

That last detail is the one part of the job the import will not do for you. The CSV carries no positions, so every imported pin arrives at the symbol’s origin, stacked one on top of another so that their names overlap and none of them can be read (Figure 1.11). Close the table, then select each pin and drag it out to the edge it belongs on, following the grouping you settled on earlier. This is the work that stays manual. Arranging pins is a judgement about readability, which is work that a spreadsheet can’t do for you.

Figure 1.11: The twelve imported pins, all landed on top of each other at the origin. The five you placed by hand are still where you left them on the left edge.

Drag the last pin into position, and you have the symbol you were shown at the start of this chapter (Figure 1.1). Save the library with “Ctrl+S”, and your new symbol is ready for use. Let’s try it out. Open a schematic, call up the Symbol Chooser, type “drv8833”, and DRV8833_PD is listed under peters_custom_Library alongside the three DRV8833 variants that ship with KiCad (Figure 1.12). The preview pane renders the body and pins you drew. It also reports “No footprint specified”, which is the current state of things since we have not yet designed a footprint for this symbol (we’ll do this in the next chapter).

Figure 1.12: The finished part in the Symbol Chooser. (1) A search for “drv8833”. (2) DRV8833_PD under peters_custom_Library, below the stock Driver_Motor entries for the TSSOP, HTSSOP and WQFN versions of the same chip. Symbol Fields

A symbol is more than a picture and a set of pins. Within a KiCad symbol, there is a small set of ‘fields’. A field is a named piece of text that travels with the part everywhere it goes. A collection of fields, along with the symbol’s visual elements, is what make one symbol useful downstream. Open the symbol’s properties from the top toolbar, and you will find them on the “General” tab.

There is a second route to the same fields. The Symbol Editor also carries a docked “Properties” panel, which KiCad sometimes calls the Properties Manager. It shows the properties of whatever is selected on the canvas, whether that is a pin, a field, or the symbol itself, and you can edit them there without opening a dialogue at all. If you do not see the panel, open it with “View”, then “Panels”, then “Properties”, or with the button on the left toolbar. I keep it open while I work, because it saves a trip to the dialogue every time I want to change a single value.

Four fields are important to define in every part. The ‘Reference’ is the designator prefix, “U” here. This annotation turns into “U1”, “U2”, and so on. The ‘Value’ is the part’s name, “DRV8833”. ‘Footprint’ names the physical land pattern the part will solder to, which we author in the next chapter and attach here. The ‘Datasheet’ field holds a link back to the document you have been reading, so that anyone who opens the schematic is one click from the source. Beyond those, you can add any custom field you like, and this is where the extra effort becomes useful: an ‘MPN’ field with the manufacturer’s part number, a supplier field linking to where you buy the part, and a tolerance or voltage rating. A few more are worth considering as your library grows: a ‘Manufacturer’ field naming the company behind the MPN, useful once you stock parts from more than one; a lifecycle ‘Status’ field such as “Active” or “NRND” (not recommended for new designs), so that you notice before a part is discontinued rather than after; and an ‘Alternate’ field naming a second-source part for anything you expect to be hard to reorder. These fields carry useful information. When you build the bill of materials in a later chapter, every one of these fields can become a column, so the effort you spend naming a part properly now is effort you do not spend searching for part numbers at ordering time. Fill the fields in once, in the library, and every board that uses the part inherits them.

Figure 1.13: The DRV8833’s fields, shown in two places at the same time. (1) The “Symbol Properties” button in the top toolbar opens the dialogue in (2). (2) The “Library Symbol Properties” dialogue, on its “General” tab, lists the “Reference”, “Value”, “Footprint”, and “Datasheet” fields from the text, already filled in for DRV8833_PD. (3) The “+” button adds a new field row; the “MPN” and “Supplier” rows above it were added this way, and hold the part’s manufacturer part number and a link to where I buy it. (4) The Symbol Editor’s own “Properties” panel, docked on the left, shows the same fields; editing a value in either place updates the other.

Multi-Unit Symbols

When you created DRV8833_PD, I asked you to leave “Number of units per package” at 1 and said we would come back to it. This is that setting. Some parts hold several identical sub-circuits in one package, and KiCad lets a single symbol represent them as separate ‘units’. For example, a quad NAND gate holds four gates and one shared pair of power pins; a dual op-amp holds two amplifiers. Rather than draw one crowded symbol with fourteen pins, you author one gate as unit A and let KiCad generate units B, C, and D automatically, all sharing the same reference designator with a letter suffix (U1A, U1B, and so on) and the same physical package.

Authoring one takes four steps:

  1. Set the count. Do this in the “New Symbol” dialogue when you create the part, or at any time afterwards on the “Units & Body Styles” tab of the symbol’s properties.
  2. Tick “All units are interchangeable” if the units really are equivalent, as the four gates of a quad NAND are. This lets you turn on “Synchronised Pin Edits” mode, where a change you make to one unit is applied to the others for you.
  3. Draw each unit in turn. The unit drop-down in the top toolbar chooses which one the canvas shows, because the editor displays only one unit at a time.
  4. Mark the shared pins. In the “Pin Properties” dialogue, tick “Common to all units in symbol” for the power pins, so that you place them once rather than once per unit.

The DRV8833 doesn’t need this. Although it contains two H-bridges, the manufacturer presents it as one part with one pinout, so we draw it as a single unit, which is why our symbol carries all its pins on one body. I mention multi-unit symbols here because you’ll meet parts that need them, and because knowing the option exists stops you from drawing four separate symbols when KiCad would happily manage one. Remember that a multi-unit symbol is still a single component in the bill of materials; the units are a convenience for the schematic, not four different parts.

Managing Your Symbol Library

Your new library needs one correction before you go any further. When you created it, you saved peters_custom_Library.kicad_sym into this chapter’s project folder, which was convenient while you were following along (Figure 1.3). For a part you mean to reuse, that is the wrong home: the day you move or rename that project folder, the global table’s entry points at nothing, and DRV8833_PD stops being available to your other designs. Move the file now to somewhere stable in your file system, a folder you keep alongside your other long-lived work, then open “Preferences” and “Manage Symbol Libraries” and point the entry at its new path.

That correction makes more sense once you know what the library actually is. A KiCad symbol library is a single .kicad_sym file that can hold many symbols, and KiCad finds it through the ‘symbol library table’, the same mechanism you registered libraries with in Volume 1. There are two related tables: the global table, whose libraries are available in every project you open, and the project table, whose libraries belong to one project. Each entry records a path to a file, which is why moving the file without correcting the entry breaks the link. Parts you expect to reuse, like this motor driver, belong in a global library kept somewhere stable in your file system; parts that only make sense for one board can stay in a project library that travels with it.

My own habit is to keep one personal library of the parts I have authored, and to give each a clear name and a consistent suffix. The dialogue you just used, “Manage Symbol Libraries”, is where all of this happens: you can add, remove, and rename library entries there, and you can immediately see which table each library belongs to. Keep the library in good order rather than using it as temporary storage. A part you draw carefully once is available to every project that follows, and you never have to draw it again.

After a year or two, your personal library will be very valuable. Every part you have ever drawn will be stored in one place. Don’t let its safety depend on your project folder alone. Back it up the way you back up anything you cannot afford to lose, and if you already use git for your own projects, then put the library under version control too. A .kicad_sym file is plain text, so git tracks every change to it cleanly, and you get a full history of every part you have added, which is useful the day a part turns out to be wrong.

A single library, as I use here, is the right choice while you are starting out, but you do not have to keep it that way forever. Once your library holds a few hundred parts, a single tree becomes hard to scan, and splitting it into a number of domain libraries (connectors, ICs, and passives, for example) keeps each one browsable. KiCad lets you create a new library and move symbols into it at any time, so the practical approach is to start with one library and split it later, once the tree view becomes difficult to navigate.

One more caution is worth knowing once you manage a library with more than the Symbol Editor alone. If you ever edit a .kicad_sym file directly, for example with a script that generates several parts at once, close the library in KiCad first. KiCad keeps its own copy of the file in memory while the library is open, and the next time it saves, it overwrites your external changes without warning.

Footprint Association

A symbol and a footprint are separate things in KiCad. The link between them is a deliberate action, meaning that you have to think carefully before you link a footprint to a symbol.

A symbol is the part on the schematic; a footprint is the copper it lands on. KiCad will let you pair any symbol with any footprint, including nonsensical pairings, and it will not complain, so the responsibility for a sensible match is yours. The link is the “Footprint” field you met a moment ago. Click into it, open the footprint chooser with the library button, and pick the land pattern that matches the part’s package.

For the DRV8833 that pattern is a sixteen-pin HTSSOP2 with an exposed thermal pad, and we have not drawn it yet, which is why the Symbol Chooser reported “No footprint specified” when you looked at the finished part (Figure 1.12). That is fine; it is the very next chapter’s work. When the footprint exists in your library, you’ll point this field at it, and from then on the two parts you authored arrive on the board as one, because the footprint association is saved with the symbol and applies every time you use it. If you have only one or two parts to associate, you can do it here, in the symbol’s properties, one at a time. When you have a whole board of parts to associate, KiCad’s footprint assignment tool sets every association in a single window, and it is the tool you reach for on a real design. Remember that whichever route you take, you are matching a schematic part to a physical one, so let the datasheet’s package drawing, not guesswork, decide the match.

You have authored your first custom symbol, given it the fields the rest of the workflow depends on, and left it pointing at a footprint you are about to build. That footprint is the more demanding part of the job, because the DRV8833’s exposed thermal pad raises real questions about copper, heat, and solder paste that a simpler package would let you avoid.
